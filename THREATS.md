# LedgerLine Threat Model & Mitigation Matrix

This document tracks security threats, mitigations, verification tests, and their current implementation status for LedgerLine.

| Threat | Mitigation | Test | Status |
|---|---|---|---|
| **1. Weak JWT Secret** (HMAC brute-force or dictionary attack) | `JwtService` validates secret length on application startup (`@PostConstruct`) and aborts startup with an `IllegalStateException` if `JWT_SECRET` is missing, blank, or shorter than 32 bytes (256 bits). Algorithm is explicitly pinned to HMAC-SHA256 (`Jwts.SIG.HS256`). | `JwtStartupValidationTest#testJwtSecretTooShortThrows` | **Handled** |
| **2. User Enumeration on Login** (side-channel timing attacks or differential error messaging) | Authentication service returns a generic `"Invalid credentials"` message for both unknown usernames and invalid passwords. Employs a constant-time comparison path by running a full 12-round BCrypt calculation against a precomputed dummy hash even when the user does not exist in the database. | `AuthSecurityIntegrationTest#testLoginFailureWrongPassword`, `testLoginFailureUnknownUser` | **Handled** |
| **3. Default Credentials in Production** | Zero hardcoded default passwords in code or configuration. `DatabaseSeeder` mandates `SEED_ADMIN_PASSWORD`, `SEED_HOLDER_PASSWORD`, and `SEED_AUDITOR_PASSWORD` via environment variables and terminates startup immediately if any are missing or blank. | `JwtStartupValidationTest#testDatabaseSeederFailsWhenPasswordMissing` | **Handled** |
| **4. Application Role Owns Tables (Privilege Escalation & Tampering)** | Principle of least privilege enforced at the PostgreSQL layer: migrations run as `ledger_owner`, while the application connects as restricted `ledger_app`. `ledger_app` does not own any table and is explicitly revoked and denied `UPDATE`, `DELETE`, and `TRUNCATE` permissions on `ledger_entries`, `postings`, `ledger_attempts`, and `audit_log`. | `DatabaseRolePermissionsIntegrationTest#testAppCannotUpdateLedgerEntries`, `testAppCannotDeleteLedgerEntries`, `testAppCannotTruncateLedgerEntries` | **Handled** |
| **5. Secrets Committed to Source Control (Git)** | `.gitignore` excludes `.env`, `.env.local`, `.idea`, build artifacts, and local tool configs. `application.yml` uses environment variable placeholders without hardcoded credentials. A `.env.example` template with dummy values is provided. | Git status verification and repository inspection | **Handled** |
| **6. Stack-Trace and Exception Class Leakage** | `server.error.include-stacktrace=never` and `server.error.include-message=never` in `application.yml`. A global `@RestControllerAdvice` (`GlobalExceptionHandler`) intercepts all checked and unchecked exceptions, returning sanitized, generic JSON error envelopes without internal class names or database details. | `AuthSecurityIntegrationTest#testLoginFailureWrongPassword` | **Handled** |
| **7. Brute-Force Login Attacks** (credential stuffing) | Bucket4j token bucket rate limiting on `/api/auth/login` per client IP (10 attempts/min) and per username (5 attempts/min). Returns `429 Too Many Requests` with `Retry-After` header. Defends against `X-Forwarded-For` spoofing unless `trusted-proxy-enabled=true`. | `Task4SecurityAndAdminIntegrationTest#testLoginRateLimitingByIpAndUsername` | **Handled** |
| **8. XSS Stealing Authentication Token** | Single-page application stores JWT strictly in React component memory state, completely avoiding `localStorage` and `sessionStorage`. **Tradeoff**: session is cleared upon browser refresh or tab closure; long-lived sessions require silent refresh with HttpOnly cookies. | Architecture review & frontend memory storage design | **Handled (tradeoff documented)** |
| **9. Permissive / Allow-by-Default Routing** | Strict deny-by-default HTTP security configuration via Spring Security: `.anyRequest().authenticated()`. Only `/api/auth/login`, `/actuator/health`, and static assets are permitted publicly. Method security (`@EnableMethodSecurity`) enforces role-based authorization on sensitive routes. | `AuthSecurityIntegrationTest#testProtectedRouteRequiresToken`, `testHolderCannotAccessAdminEndpoint`, `testAdminCanAccessAdminEndpoint` | **Handled** |
| **10. Mass-Assignment of Role on User Creation** | No public user registration endpoint. Seed and internal user creation strictly bind the `UserRole` enum within service logic. No external API payload accepts role manipulation parameters. | Architecture review & DTO inspection | **Handled** |
| **11. Account Overdraft (Race Condition & Double-Spend)** | All involved accounts locked exclusively via `SELECT ... FOR UPDATE` before balance check. Balances checked against locked rows; updates use `Math.subtractExact` / `Math.addExact`. In addition, PostgreSQL enforces `CHECK (type <> 'USER' OR balance >= 0)` on the `accounts` table. | `LedgerEngineIntegrationTest#testInsufficientFundsRefusalRecorded`, `testReversalRefusedIfWouldOverdraw` | **Handled** |
| **12. Opposing Concurrent Transfer Deadlock** | Concurrent transfers between identical accounts in opposite directions (A->B and B->A) can produce cyclic deadlocks in relational databases. Mitigated by sorting involved account IDs in strict numerical ASCENDING order (`lockAccountsInOrder`) prior to acquiring locks. | `LedgerEngineIntegrationTest#testOppositeDirectionTransfersDoNotDeadlock` | **Handled** |
| **13. Direct Database Ledger Tampering (UPDATE / DELETE / TRUNCATE)** | Enforced at both role level (`ledger_app` denied permissions) and database engine level via `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers on `ledger_entries`, `postings`, `ledger_attempts`, and `audit_log`, rejecting modifications even from the table owner. | `LedgerEngineIntegrationTest#testAppendOnlyTriggersBlockMutationsEvenForOwner`, `DatabaseRolePermissionsIntegrationTest` | **Handled** |
| **14. Unbalanced Double-Entry Postings (Zero-Sum Violation)** | Database constraint trigger `check_entry_zero_sum` on `postings` table marked `DEFERRABLE INITIALLY DEFERRED`. At transaction commit, checks that `SUM(amount) = 0` for all postings of an entry, throwing an unrecoverable exception if non-zero. | `LedgerEngineIntegrationTest#testRawUnbalancedEntryRejectedAtCommitByTrigger` | **Handled** |
| **15. Double-Reversal / Multiple Reversals of Entry** | Database unique partial index `idx_ledger_entries_reverses_unique` on `ledger_entries(reverses_entry_id) WHERE reverses_entry_id IS NOT NULL` guarantees that no entry can ever be reversed more than once. Service also verifies status before executing. | `LedgerEngineIntegrationTest#testAdministrativeReversal` | **Handled** |
| **16. Unauthorized / IDOR Account Debit** | All debit operations verify that the authenticated caller (extracted from verified JWT, never trusted from client payload) is a confirmed member of the source account in `account_members`. Unauthorized attempts are refused and recorded. | `LedgerEngineIntegrationTest#testUnauthorizedRefusalRecorded` | **Handled** |
| **17. Check-Then-Insert Idempotency Race Condition** | In-flight check-then-insert is susceptible to two concurrent transactions both seeing "key not found" and executing duplicate money movements. Mitigated by performing atomic `INSERT INTO idempotency_keys (... status='IN_PROGRESS') ON CONFLICT (user_id, key) DO NOTHING` in the *same* transaction as the money move. If insert succeeds, transaction owns the key; if it conflicts, it blocks on the row lock until the owner commits/aborts. | `IdempotencyAndAuditIntegrationTest#testTransferIdempotencyReplay` | **Handled** |
| **18. Key Collision Across Different Users (Key Hijacking)** | If idempotency keys were globally scoped, User A could guess or collide with User B's key, causing User B's transfers to fail or replay User A's response. Mitigated by scoping `idempotency_keys` strictly to `UNIQUE(user_id, key)` and including `userId` in the canonical request hash calculation. | `IdempotencyAndAuditIntegrationTest#testTransferIdempotencyReplay`, `CanonicalRequestHasher` | **Handled** |
| **19. Duplicate Refusal Generation on Replay** | Replaying a refused request must return the identical refusal without inserting duplicate rows into `ledger_attempts`. Mitigated by committing the initial refusal response status and JSON into `idempotency_keys`. On replay with matching hash, the cached refusal is directly returned and `duplicate_count` is incremented without invoking `move()`. | `IdempotencyAndAuditIntegrationTest#testRefusedReplayReturnsSameRefusalWithoutNewAttempt` | **Handled** |
| **20. Request Payload Tampering with Existing Key (Parameter Mutation)** | An attacker submits an idempotency key with an initial small amount, then re-submits the same key with an altered larger amount or different destination account. Mitigated by computing a SHA-256 hash over canonical `(method, path, userId, sortedJsonBody)`. Any change in payload produces a hash mismatch, rejecting the request with `422 Unprocessable Entity` without moving funds. | `IdempotencyAndAuditIntegrationTest#testSameKeyDifferentPayloadRejectedWith422` | **Handled** |
| **21. Key Collision via Whitespace Tampering** | Differences in leading, trailing, or internal whitespace in idempotency keys (`"key"`, `" key "`, `"key with space"`) could lead to accidental or malicious key fragmentation. Mitigated by strict key validation (`key.contains(" ") || !key.equals(key.trim()) || length > 128`) which rejects invalid or whitespace-tainted keys with `400 Bad Request`. | `IdempotencyAndAuditIntegrationTest#testInvalidIdempotencyKeysRejectedWith400` | **Handled** |
| **22. Concurrent In-Flight Replay Race** | A second request arrives with the same key while the first transaction is actively in-flight. Mitigated by PostgreSQL row-level locks on the unique index tuple during `INSERT ... ON CONFLICT DO NOTHING`. The second transaction waits for the first transaction to complete. If the first commits, the second re適lays the completed response; if the first rolls back, the second assumes ownership cleanly. | `IdempotencyService` design & PostgreSQL transaction lock mechanics | **Handled** |
| **23. Audit / Ledger Chain Forking Across Concurrent Transactions** | When appending to a cryptographic hash chain (`hash = SHA-256(prev_hash || payload)`), two concurrent transactions might both read the same `prev_hash`, creating a fork in the chain. Mitigated by acquiring transaction-scoped advisory locks (`pg_advisory_xact_lock`) before reading `prev_hash`, forcing strict serialization of chain appends. | `AuditRepository#acquireAuditLock`, `LedgerRepository#acquireLedgerLock` | **Handled** |
| **24. Undetected Database Superuser Data Tampering** | Even if a superuser bypasses DB triggers to alter row data or balances, the cryptographic hash chains in `audit_log` and `ledger_entries` link every row to its predecessor using SHA-256. Any modification to a payload or hash causes `verifyAuditLogChain()` and `verifyLedgerEntriesChain()` to fail forensic verification immediately. | `IdempotencyAndAuditIntegrationTest#testAuditAndLedgerHashChainVerificationAndTamperDetection` | **Handled** |
| **25. Statement Access Control & Account Existence Enumeration** | Unauthorized users querying `/api/accounts/{id}/statement` must not observe account transactions or deduce whether an account ID exists. Mitigated by returning `404 Not Found` (rather than `403 Forbidden`) whenever the caller is neither an account member, ADMIN, nor AUDITOR. | `IdempotencyAndAuditIntegrationTest#testStatementEndpointAndAuthorization` | **Handled** |
| **26. IDOR on Statement** | Any unauthorized user attempting to read another user's account statement is blocked. A single-query membership check (`findAccountWithMembership`) verifies caller membership or ADMIN/AUDITOR role. Non-members receive a generic `404 Not Found`, hiding data and preventing ID existence leaking. | `Task4SecurityAndAdminIntegrationTest#testHolderCannotReadOrMoveOtherUserAccount` | **Handled** |
| **27. IDOR via Idempotency Key of Another User** | A user guessing or reusing another user's idempotency key cannot replay or tamper with transactions. The `idempotency_keys` table enforces `UNIQUE(user_id, key)` composite key, and all queries filter strictly on the authenticated `user_id`. Key namespaces are completely isolated per user. | `IdempotencyAndAuditIntegrationTest#testTransferIdempotencyReplay` | **Handled** |
| **28. Role Escalation / Mass Assignment** | Callers attempting to elevate privilege or tamper with balances/user assignments via request bodies. Mitigated by omitting `role`, `userId`, and `balance` fields from all request DTOs (`CreateAccountRequest`, `AddMemberRequest`, `AmountRequest`, `TransferRequest`, `AdjustRequest`). User identity is extracted strictly from the cryptographically verified JWT (`SecurityContextHolder`). Deserialization rejects unknown fields (`FAIL_ON_UNKNOWN_PROPERTIES = true`). | `Task4SecurityAndAdminIntegrationTest#testAuditorCannotCallAnyWriteRoute`, DTO review | **Handled** |
| **29. Negative, Huge, or Decimal Amounts** | Attackers sending negative amounts (to reverse flow), huge numbers (to trigger integer overflow), or decimals/fractions. Mitigated by `@Min(1)`, `@Max(100_000_000_000L)` validation annotations, `Math.addExact` / `Math.subtractExact` overflow checking, and Jackson scalar coercion rejection (`LogicalType.Integer` coercion from `String` and `Float` set to `Fail`). | `Task4SecurityAndAdminIntegrationTest#testInputValidationRejectsInvalidAmountsAndUnknownFields` | **Handled** |
| **30. JSON Type Confusion & Unknown Fields** | Attackers injecting strings, booleans, floating-point numbers, or extra unauthorized JSON keys. Jackson `ObjectMapper` is configured with `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES = true` and `coercionConfigFor(LogicalType.Integer).setCoercion(CoercionInputShape.String, CoercionAction.Fail)`. Any type confusion yields generic `400 Bad Request`. | `Task4SecurityAndAdminIntegrationTest#testInputValidationRejectsInvalidAmountsAndUnknownFields` | **Handled** |
| **31. 404 vs 403 Information Oracle (Account Existence Leakage)** | Discrepancies in HTTP response codes (404 vs 403) or database query response timing allowing attackers to enumerate valid account UUIDs. Mitigated by returning constant `404 Not Found` with identical generic JSON body for both nonexistent accounts and unowned accounts. A single SQL query with `EXISTS` executes the exact same query plan and constant execution time. | `Task4SecurityAndAdminIntegrationTest#testHolderCannotReadOrMoveOtherUserAccount` | **Handled** |
| **32. Header Spoofing for Rate Limit Bypass** | Attackers rotating or forging `X-Forwarded-For` HTTP headers to bypass per-IP login throttling. Mitigated by evaluating `ledgerline.rate-limit.trusted-proxy-enabled`. When false (direct connection), `request.getRemoteAddr()` is used directly and spoofed headers are ignored. When true (behind trusted reverse proxy e.g. Render/ALB), the proxy-set client IP is safely resolved. | `RateLimiterService#resolveClientIp`, `Task4SecurityAndAdminIntegrationTest#testLoginRateLimitingByIpAndUsername` | **Handled** |
| **33. Verify Endpoint Denial of Service (DoS)** | Long-running verification queries locking tables or causing database contention. The `GET /api/admin/verify` endpoint runs in a read-only transaction (`@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)`). In PostgreSQL, readers never block writers and writers never block readers (MVCC snapshot isolation). Zero row or table locks are held, preventing lock contention or DoS. | `SystemVerificationService#verifySystem`, `Task4SecurityAndAdminIntegrationTest#testVerifyEndpointPassesAndDetectsTampering` | **Handled** |

## Route Authorisation Matrix

All routes enforce **deny-by-default**. Any endpoint not explicitly matched below requires authentication and method-level role check.

| HTTP Method | Route Path | Allowed Roles | Ownership / Membership Check | Missing Permission Response |
|---|---|---|---|---|
| `POST` | `/api/auth/login` | *Public (PermitAll)* | N/A (credentials verified against bcrypt hash) | `401 Unauthorized` (generic message) |
| `GET` | `/actuator/health` | *Public (PermitAll)* | N/A (readiness/liveness check) | N/A |
| `GET` | `/api/accounts` | `HOLDER`, `ADMIN`, `AUDITOR` | `HOLDER`: filtered strictly to accounts where `account_members.user_id = auth_user_id`. `ADMIN`/`AUDITOR`: all accounts. | `401 Unauthorized` / Empty list for non-member |
| `GET` | `/api/accounts/{id}` | `HOLDER`, `ADMIN`, `AUDITOR` | `HOLDER`: Must be member of `{id}`. `ADMIN`/`AUDITOR`: Any account. | `404 Not Found` (indistinguishable from nonexistent) |
| `GET` | `/api/accounts/{id}/statement` | `HOLDER`, `ADMIN`, `AUDITOR` | `HOLDER`: Must be member of `{id}`. `ADMIN`/`AUDITOR`: Any account. | `404 Not Found` (indistinguishable from nonexistent) |
| `POST` | `/api/accounts/{id}/deposit` | `HOLDER`, `ADMIN` | Destination must exist. Caller member check verified. Idempotent per user. | `404 Not Found` (if non-member) / `403` (AUDITOR) |
| `POST` | `/api/accounts/{id}/withdraw` | `HOLDER`, `ADMIN` | Caller must be member of source account `{id}`. Non-member move records `REFUSED` attempt and returns 404. | `404 Not Found` (if non-member) / `403` (AUDITOR) |
| `POST` | `/api/transfers` | `HOLDER`, `ADMIN` | Caller must be member of `fromAccountId`. Transfer TO any account permitted. Non-member move records `REFUSED` attempt and returns 404. | `404 Not Found` (if non-member) / `403` (AUDITOR) |
| `POST` | `/api/admin/accounts` | `ADMIN` only | N/A (admin privilege required). Creates `USER` account, currency `INR`. | `403 Forbidden` (for HOLDER, AUDITOR) |
| `POST` | `/api/admin/accounts/{id}/members` | `ADMIN` only | N/A (admin privilege required). Grants user membership to account `{id}`. | `403 Forbidden` (for HOLDER, AUDITOR) |
| `POST` | `/api/admin/accounts/{id}/adjust` | `ADMIN` only | N/A (admin privilege required). Audited `ADJUSTMENT` ledger entry; respects non-negative rule. | `403 Forbidden` (for HOLDER, AUDITOR) |
| `POST` | `/api/admin/entries/{id}/reverse` | `ADMIN` only | N/A (admin privilege required). Reverses entry `{id}` exactly once; respects non-negative rule. | `403 Forbidden` (for HOLDER, AUDITOR) |
| `GET` | `/api/admin/verify` | `ADMIN`, `AUDITOR` | Read-only system integrity verification running in `REPEATABLE READ` snapshot. | `403 Forbidden` (for HOLDER) |
